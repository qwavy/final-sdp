# Parcel Hub — проект по ТЗ

Этот файл объясняет, **что** сделано и **как это закрывает требования ТЗ**.
Разбор кода «как это работает внутри» — в [CODE.md](CODE.md).

---

## 1. Идея

**Parcel Hub** — программа для сотрудника пункта выдачи заказов (ПВЗ) или службы доставки.

**Проблема:** посылки нужно принять, посчитать стоимость доставки, отдать курьеру,
отслеживать, где посылка сейчас, сообщать клиенту об изменениях и в конце дня
понимать, сколько заказов и денег было.

**Пользователь:** оператор ПВЗ / диспетчер доставки.

**Полный путь пользователя (как требует ТЗ: создать → настроить → действие → результат):**

1. **Создать** — новый заказ: клиент, что внутри, вес, ценность.
2. **Настроить** — способ доставки (до двери / ПВЗ / постамат), доп. услуги
   (страховка, хрупкое, срочно), способ расчёта цены (по весу / по расстоянию).
3. **Выполнить действие** — назначить курьера (ближайший / наименее загруженный),
   провести заказ по статусам: Создан → Курьер назначен → В пути → (Ждёт в точке выдачи) → Выдан.
4. **Посмотреть и сохранить результат** — отчёт за день, выгрузка в CSV или JSON.

## 2. Domain (предметная область) — что это вообще

**Domain** — это «мир», который программа описывает: какие в нём есть объекты и какие правила.
В коде это папка `backend/internal/domain`. Там **нет** ничего про HTTP, файлы или браузер —
только бизнес-логика. Поэтому её легко тестировать и объяснять.

### Сущности (ТЗ: минимум 3 связанные)

| Сущность | Что это | Связи |
|---|---|---|
| **Order** (заказ) | Главный объект: посылка, способ доставки, цена, статус, история | ссылается на Customer, Courier, PickupPoint |
| **Customer** (клиент) | Имя и телефон того, кому везут | у клиента много заказов |
| **Courier** (курьер) | Имя, телефон, район, вместимость (сколько заказов везёт одновременно) | у курьера много заказов |
| **PickupPoint** (точка выдачи) | ПВЗ или постамат с адресом и районом | в точку приходит много заказов |

### Объекты-значения (value objects)

- **Money** — сумма в тенге (целое число).
- **District** — район города и его координаты на упрощённой карте (для расстояний).
- **OrderStatus** — статус заказа.
- **PriceLine** — строка расшифровки цены («Страховка — 800 ₸»).

### Главные бизнес-правила (живут в domain)

- Заказ создаётся только **целиком корректным** (Builder проверяет все поля).
- У каждого способа доставки **свой лимит веса**: дверь — 50 кг, ПВЗ — 30 кг, постамат — 15 кг.
- Статусы меняются **только по разрешённым переходам**. Доставка до двери не проходит
  через «Ждёт в точке выдачи», а доставка в ПВЗ — обязательно проходит.
- Курьер не может взять больше заказов, чем его **вместимость**.
- Изменять заказ можно только пока он в статусе **«Создан»**.
- Удалить можно только **новый или завершённый** заказ.
- Нельзя удалить **клиента с активными заказами** или **курьера с активными заказами**.
- Для **страховки** нужна объявленная ценность больше 0.
- Телефон клиента **уникален**.

### События

Когда команда меняет заказ (создан, изменён, удалён, сменился статус), она оповещает
наблюдателей (паттерн Observer, см. ниже). Сам domain о событиях ничего не знает.

## 3. Архитектура

**Гексагональная архитектура (ports & adapters) + DDD-lite + CQS.**

```
            ┌──────────────── adapters/in ────────────────┐
 браузер ──►│ http: REST API                              │
            └──────────────────────┬──────────────────────┘
                                   ▼
            ┌──────────────── application ────────────────┐
            │ Facade → command (меняют) / query (читают)  │
            │ events: Observer (Publisher + наблюдатели)  │
            │ port: интерфейсы для внешнего мира          │
            └──────────────────────┬──────────────────────┘
                                   ▼
            ┌────────────────── domain ───────────────────┐
            │ сущности, правила, Builder, Strategy, ...   │
            └─────────────────────────────────────────────┘
            ┌──────────────── adapters/out ───────────────┐
            │ storage: JSON-файлы   notify: SMS-шлюз      │
            └─────────────────────────────────────────────┘
```

- **Domain** — правила. Ни от чего не зависит.
- **Application** — сценарии (use cases): «создать заказ», «назначить курьера».
  Работает с хранилищем только через интерфейсы (`port`).
- **Adapters** — связь с внешним миром: HTTP на входе, файлы и SMS на выходе.

**Зачем так:** ТЗ требует разделить интерфейс, бизнес-логику и хранение данных.
Здесь их можно менять независимо: перейти с JSON на базу данных — новый адаптер,
домен и сценарии не меняются.

**DDD-lite:** берём из DDD богатые сущности (правила внутри `Order`, `Courier`)
и value objects. Без «тяжёлых» частей (bounded contexts и т.п.) — для
такого размера проекта они лишние.

**CQS (Command–Query Separation):** команды **меняют** данные и ничего не возвращают,
кроме ошибки (и ID нового объекта). Запросы **только читают**. Это папки
`use_cases/command` и `use_cases/query`.

## 4. Паттерны (7 штук: 2 порождающих, 3 структурных, 2 поведенческих)

ТЗ требует минимум 6, включая хотя бы по одному каждого типа. Седьмой (Adapter) — запасной.

### Builder — порождающий

- **Проблема:** у заказа ~10 полей, часть обязательна только для одного способа доставки
  (адрес — для двери, точка выдачи — для ПВЗ/постамата). Нужно, чтобы некорректный
  заказ невозможно было создать.
- **Решение:** `OrderBuilder` собирает заказ по шагам, а `Build()` проверяет всё разом,
  считает расстояние и цену и возвращает готовый заказ — или список ошибок по полям.
- **Где:** `domain/order_builder.go`.
- **Как показать:** нажать «Создать заказ» с пустой формой — ошибки подсветятся у всех полей.
- **Ограничение:** Builder в Go — обычный тип с цепочкой методов; Director (из классической
  схемы GoF) не нужен, его роль играет команда `OrderCommands.build`.

### Factory Method — порождающий

- **Проблема:** способы доставки отличаются тарифом, лимитом веса, необходимостью точки
  выдачи и цепочкой статусов. Не хочется писать `switch` по типу доставки по всему коду.
- **Решение:** интерфейс-продукт `DeliveryMethod` и создатели `DeliveryCreator`
  с фабричным методом `CreateMethod()`. Остальной код работает только с интерфейсом.
- **Где:** `domain/delivery.go`.
- **Как показать:** создать заказ в постамат весом 16 кг и нажать «Создать» — ошибка «максимум 15 кг»;
  заказ «до двери» после «В пути» сразу предлагает «Выдан», а заказ в ПВЗ — «Ждёт в точке выдачи».
- **Ограничение:** в Go нет наследования, поэтому Creator — интерфейс, а не абстрактный класс.

### Decorator — структурный

- **Проблема:** доп. услуги можно комбинировать как угодно (0, 1, 2 или 3 услуги).
  Отдельный класс на каждую комбинацию — это 8 классов, и их число растёт с каждой услугой.
- **Решение:** базовая цена (`basePrice`) и обёртки (`insurance`, `fragile`,
  `express`). Каждая обёртка реализует тот же интерфейс `PriceComponent` и добавляет своё.
- **Где:** `domain/price.go`.
- **Как показать:** в форме заказа отмечать галочки услуг — меняются строки расшифровки и итог.
  «Срочно» даёт +50% от **всей** суммы под ней — видно, что обёртки вкладываются друг в друга.
- **Ограничение:** важен порядок обёрток (срочность всегда последней), он задан списком `extras`.

### Facade — структурный

- **Проблема:** чтобы, например, создать заказ и показать его, нужно вызвать команду,
  потом запрос, а им нужны репозитории и шина событий. HTTP-слой не должен это знать.
- **Решение:** `DeliveryFacade` — одна точка входа с простыми методами (`CreateOrder`,
  `AssignCourier`, `DailyReport`…).
- **Где:** `application/facade.go`.
- **Как показать:** открыть `adapters/in/http/handlers.go` — каждый обработчик вызывает
  ровно один метод фасада.
- **Ограничение:** фасад может разрастись; если методов станет много, его делят на несколько.

### Adapter — структурный (запасной)

- **Проблема:** «сторонний» SMS-шлюз имеет неудобный интерфейс: телефон без `+`,
  текст до 160 символов, результат — числовой код, а не ошибка. Менять его мы не можем.
- **Решение:** приложение ждёт интерфейс `port.Notifier`. `SmsNotifier` реализует его
  и внутри переводит вызов в формат шлюза.
- **Где:** `adapters/out/notify/sms.go`.
- **Как показать:** сменить статус заказа — в журнале запись «SMS на +7…», в файле
  `backend/data/sms_outbox.txt` строка с номером без `+`.

### Strategy — поведенческий (используется дважды)

- **Проблема:** ТЗ требует, чтобы пользователь выбирал из двух способов выполнить операцию.
- **Решение 1 — расчёт цены:** `PricingStrategy` → `WeightPricing` (по весу)
  и `DistancePricing` (по расстоянию). Файл `domain/pricing.go`.
- **Решение 2 — выбор курьера:** `CourierSelector` → `NearestCourier` (ближайший)
  и `LeastLoadedCourier` (наименее загруженный). Файл `domain/courier_selection.go`.
- **Как показать:** в форме заказа две цены рядом — кликнуть по любой; в карточке заказа
  выбрать стратегию курьера перед «Назначить курьера».
- **Ограничение:** стратегии регистрируются в списке; новую нужно не забыть туда добавить.

### Observer — поведенческий

- **Проблема:** смена статуса должна вызывать несколько независимых реакций:
  запись в журнал и SMS клиенту. Команда не должна знать о каждой.
- **Решение:** `events.Publisher` (Subject) хранит список наблюдателей и в `Notify`
  вызывает у каждого `Update(event)`. Наблюдатели: `ActivityRecorder` (журнал)
  и `CustomerNotifier` (SMS).
- **Где:** `application/events/observer.go`, подписка в `cmd/server/main.go`.
- **Как показать:** сменить статус — в «Журнале событий» появляются две записи
  (смена статуса и SMS), в `backend/data/sms_outbox.txt` — новая строка.
- **Ограничение:** рассылка синхронная — медленный подписчик тормозит запрос.

### Итоговая таблица (для отчёта)

| Pattern | Problem it solves | Main classes/interfaces | How to demonstrate it | Responsible student |
|---|---|---|---|---|
| Builder | Корректное создание заказа со многими полями | `OrderBuilder` | Пустая форма → ошибки по полям | _ваше имя_ |
| Factory Method | Разные способы доставки без `switch` | `DeliveryCreator`, `DeliveryMethod` | Лимит веса постамата, разные цепочки статусов | _ваше имя_ |
| Decorator | Доп. услуги в любой комбинации | `PriceComponent`, `insurance`, `fragile`, `express` | Галочки услуг меняют расшифровку цены | _ваше имя_ |
| Facade | HTTP не знает о внутренних подсистемах | `DeliveryFacade` | Обработчики вызывают один метод фасада | _ваше имя_ |
| Adapter | Несовместимый интерфейс SMS-шлюза | `Notifier`, `SmsNotifier`, `SmsGateway` | Смена статуса → `sms_outbox.txt` | _ваше имя_ |
| Strategy | Выбор способа расчёта цены и курьера | `PricingStrategy`, `CourierSelector` | Две цены в форме; выбор стратегии курьера | _ваше имя_ |
| Observer | Независимые реакции на смену статуса | `Publisher`, `Observer`, `ActivityRecorder`, `CustomerNotifier` | Журнал и SMS после смены статуса | _ваше имя_ |

## 5. Как закрыты остальные требования ТЗ

| Требование | Как закрыто |
|---|---|
| ≥ 3 связанные сущности | Order, Customer, Courier, PickupPoint |
| ≥ 5 сценариев | создать заказ, настроить услуги и цену, назначить курьера, сменить статус / отменить, отчёт; плюс CRUD клиентов и курьеров |
| Создание, просмотр, редактирование, удаление | заказы, клиенты, курьеры; отмена заказа — статус «Отменён» |
| Взаимозаменяемое поведение | Strategy: 2 способа расчёта цены, 2 способа выбора курьера |
| Реакция на событие | Observer: запись в журнал и SMS клиенту |
| Сохранение после перезапуска | JSON-файлы в `backend/data/` |
| Итоговый результат с сохранением | отчёт за день, выгрузка CSV/JSON + копия в `backend/data/exports/` |
| Валидация и ошибки | ошибки по полям (422), нарушение правил (409), не найдено (404), битый JSON (400) |
| Тестовые данные | загружаются при первом запуске автоматически |
| GUI | React + shadcn: вкладки Заказы, Клиенты, Курьеры, Журнал, Отчёт |

## 7. Сценарий демонстрации на защите (≈ 5 минут)

1. Вкладка **Заказы** → «Новый заказ» → сразу «Создать» → показать ошибки (**Builder**, валидация).
2. Заполнить: клиент, «Чайный сервис», 3.2 кг, ценность 40 000, **постамат** →
   ввести 16 кг → «Создать заказ» → ошибка «максимум 15 кг» (**Factory Method**) → вернуть 3.2.
3. Отметить «Страховка» и «Хрупкое» → строки в расшифровке (**Decorator**).
4. Сравнить две цены и выбрать одну (**Strategy**) → «Создать заказ».
5. Выбрать «Наименее загруженный» → «Назначить курьера» (**Strategy**).
6. «В пути» → «Ждёт в точке выдачи» → «Выдан».
7. Вкладка **Журнал** → события и SMS (**Observer** + **Adapter**).
8. Вкладка **Отчёт** → «Выгрузить CSV» (итоговый результат).
9. Перезапустить сервер → данные на месте (сохранение).
10. Открыть `handlers.go` → обработчики вызывают только фасад (**Facade**).

## 8. Будущие улучшения (для раздела Future Work)

- Настоящая база данных (PostgreSQL) — новый адаптер `out/storage`, без изменений в domain.
- Настоящая отправка SMS / Telegram — ещё один адаптер под `port.Notifier`.
- Учётные записи и роли (оператор, курьер, администратор).
- Карта с реальными адресами вместо упрощённых районов.
- Асинхронная рассылка событий (очередь), чтобы медленный подписчик не тормозил запрос.
- Живое обновление экрана у всех пользователей (WebSocket / Server-Sent Events) — ещё один Observer.
